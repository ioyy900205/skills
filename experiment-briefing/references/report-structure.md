# 页面结构与表达

这份参考解决一件事：让报告能被快速扫读，同时不牺牲证据完整性。

## 第一屏原则

第一屏不是“目录”，而是答案。

读者只看第一屏，也应该知道：

- 这次在解决什么。
- 当前最重要的结论或状态。
- 规模/影响有多大。
- 有什么必须注意的限制。
- 如果需要读者行动：需要他决定或支持什么。

没有真实 Decision / Ask 时不要硬造。

## 实验结果结构

默认：

Hero → 概念铺垫（可选）→ 方法 → 主结果 → 全条件证据 → 边界归因 → 口径与限制 → 复现。

标题写结论，不写主题。

差：“干信比 × 时频重叠实验报告”。

好：“干扰比信号强 25 dB 时，模型主要丢失的是数量判断，而不是目标存在性”。

Hero 通常包含 3–4 个 KPI 与一句实验规模。KPI 必须写清“什么数字、在什么范围、与什么比”。

## 项目阶段总结结构

默认：

Hero → Goal / Scope → Progress → Outcomes / Evidence → Risks & Dependencies → Decisions / Open Questions → Next Actions / Asks → Sources。

这里最重要的不是“做了多少事”，而是：

**目标 → 已发生的事实 → 与计划的差距 → 对项目意味着什么 → 下一步。**

如果项目有明确里程碑，可用 planned vs actual 表格；如果没有可靠计划基线，不要伪造“偏差”。

## 项目复盘结构

默认：

Hero → Planned vs Actual → Timeline → Outcomes → What Worked → What Didn't → Contributing Factors → Lessons → Actions。

只有时间线本身能帮助理解因果/决策时才放；不要为了形式列流水账。

## Hero

2–3 句即可：

1. 结论/状态。
2. 最重要的证据或影响。
3. 必要时：主要风险/限制或 Decision / Ask。

避免“本项目围绕……开展了……”这种没有信息量的开头。

## 主结果与项目证据

图是证据，不是结论。每张核心图后面写 3–5 条要点：

- 主要趋势。
- 对比。
- 异常/反直觉结果。
- caveat。
- 需要继续验证的点。

项目进展也一样：不要只列“完成 A/B/C”，要说明这些交付对目标产生了什么结果；如果暂时只有产出没有 outcome，就明确写“当前仅验证到产出层”。

## Open Questions

把真正未解决、会影响判断的问题单独列出。

好问题应该满足至少一条：

- 答案会改变当前结论。
- 答案会改变下一步优先级。
- 当前材料存在冲突。
- 关键数据缺失。

不要把普通 TODO 混进 Open Questions。

## Next Actions / Asks

Action 是执行事项；Ask 是需要读者给资源、决策或解除阻塞。

Action 最好包含：动作、owner、due、done criteria；来源没有这些字段时写 TBC，不猜。

Ask 要具体，例如“确认是否继续投入 2 周做真实设备采集”，而不是“希望领导支持”。

## 图表与布局

优先内联 SVG；谱图/照片等位图用 PNG/WebP。

原则：

- 一个图回答一个问题。
- 轴、单位、时间范围明确。
- 多配置优先 tab，不横向挤。
- 状态不能只靠颜色；必须有文字/形状。
- 颜色在亮/暗模式都可读。
- 长表可折叠，主结果默认展开。

如果环境有专门数据可视化 skill，可在复杂图表前参考；不存在时不要把它当硬依赖。

## Sources

项目总结往往综合代码、提交、会议、日志、文档和用户输入。报告底部应列出实际使用过的主要来源，具体到别人能复核：

- 文件/路径
- commit / PR / issue
- 运行目录/summary
- 会议或用户提供的材料
- 外部 URL

来源列表是为了核验，不是把原始材料整段复制进去。
