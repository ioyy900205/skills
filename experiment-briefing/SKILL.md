# 实验汇报页

一页 HTML，两种读者：**领导三十秒要拿到结论**，**自己三个月后要能追溯每个数字怎么来的**。
这两件事不冲突，靠分层解决——结论和关键数字在最前面，证据和口径在后面。
本 skill 是把这套结构、几条硬规矩和配套工具固化下来。

## 地基：生成器是唯一真相源

**先有可读回的运行结果，再有页面。** 页面里的每一个数字都从运行目录读出来，不手敲。

这不是洁癖。手敲的数字会在下一次重跑后变成谎言，而且没人知道它什么时候开始撒谎的。
从数据读回还有个副作用很值钱：**你会被迫发现自己预设的叙事不成立**——
本项目上一轮就是这样，原本要写"干扰越强检出越差"，读回来的数据说检出根本不受影响、
瓶颈在别处，于是整页重写。如果数字是手敲的，那次重写不会发生。

所以：

- 写一个 `<主题>_report.py`，输入是运行目录，输出是 `index.html`。
- 改页面 = 改这个脚本，**永远不要手改生成出来的 HTML**。在脚本顶部就写明这一点。
- 叙述里的数字也从数据读：不要写"检出率 93%"，要写 `{pct(grid_mean(run, lead, ...))}`。
  一句话里嵌三个变量看着笨，但它保证正文和图表不会各说各话。
- 结论性的句子同样要能被数据推翻。如果读回来的数字和你想写的话矛盾，**改话，不改数**。

如果运行结果还没有结构化的汇总（只有日志或散落的图），先补一个汇总 JSON 再做页面。
这一步省不掉——省掉它就只能手敲。

## 页面骨架

按这个顺序，缺哪节就跳过，但不要重排——顺序本身就是"结论先行"：

| 节 | 作用 | 关键 |
|---|---|---|
| **Hero** | 标题即结论 + 3–4 个 KPI + 一句规模说明 | 领导只读这块 |
| **概念** | 只在读者不熟这个领域时才要 | 用他熟悉领域的类比切入 |
| **方法** | 怎么造的/怎么测的 | 要让人能挑毛病 |
| **主结果** | 核心图表 + "这几张图说了什么" | 图后面必须跟要点列表 |
| **全条件证据** | 每个条件都在，包括失败的 | 不挑成功的 |
| **边界归因** | 哪些失败是原理性的，哪些是能改的 | 不写这节，表会被读反 |
| **口径与限制** | 这页答不了什么 | 写在页内，不是附录 |
| **复现** | 命令 + 配置/数据/权重哈希 | 三个月后的自己 |

### 标题是结论，不是主题

「干信比 × 时频重叠实验报告」是主题。
「干扰比信号强 25 分贝时，模型丢的不是信号，是"有几台"」是结论。
后者让人想往下读，前者让人想关掉。

### KPI 要是对比，不是孤立数字

`93%` 单独放着没有意义。有意义的是它旁边那行小字：「同形态全网格平均，与干扰强度基本无关」。
四张 KPI 卡应该合起来讲一个完整的故事——扫了多大范围、好消息是什么、坏消息是什么。

### 每张图后面跟要点列表

图是证据，不是结论。看图的人需要被告知"该看出什么"。
写成 3–5 条 `<li>`，每条一个发现，加粗的是转折词和关键数字，不是整句。
其中至少有一条应该是限定或反直觉的——全是好消息的列表读起来像广告。

## 让领导三十秒看懂

- **加粗要吝啬。** 一段里加粗超过两处，等于没加粗。加粗给关键数字和转折，不给形容词。
- **一节只讲一件事。** 讲不完就拆成两节。
- **数字带单位和方向。** 「60%」不如「60% 的窗口分得开」。
- **导航栏列出所有章节**，让人能直接跳到关心的部分。
- **不要把限制藏起来。** 领导发现被藏了一次，后面所有页都不可信了。
  限制写在页内、用正常字号，和结论平级。

## 诚实的展示

这是这套做法里最值钱的部分，也最容易在赶进度时被丢掉。

**覆盖全条件，不做只挑成功的画廊。** 全条件证据那一节要放**全部**条件的图，
包括模型什么都没报出来的。挑着放会让人（包括三个月后的你自己）高估结果。
条件多的时候用网格图：一张图里 N 行 × M 列，每格一个条件，格子标题写该格的判定结论。

**没跑成的条件要标出来，并说明为什么。** 「未合成（余量不足）」和「这一格得分为零」
是完全不同的两件事，不能共用一种画法。

**区分"原理上做不到"和"模型不够好"。** 这一节必须写。
如果某个条件下输入里根本没有区分两个目标的信息，那里的失败是信息极限，不是能力不足；
反过来，信息充足却失败了，那才是该跟进的。不讲清楚，读者会把物理极限记成模型缺陷，
或者把真正的缺陷当成"没办法的事"。

**阴性结果照样写。** 预期的效应没出现，本身就是结果。上一轮预期"强宽带干扰会选择性
压住带内的窄带突发"，实测带内 11%、带外 10%，没有选择性——这条写进了页面，
还顺带牵出一个更要紧的口径问题（发射体级"检出 100%"掩盖了逐突发只有 10% 被框出）。

**数据推翻预设时，重写叙事。** 不要把新数据硬塞进旧结构里。

**分清证据的强度等级，不要并排写成一条因果链。** 不同方法拿到的数字，能断言的东西不一样：

| 类型 | 能说的话 | 例子 |
|---|---|---|
| 恒等式/精确记账 | 「**占多少**」，各项加得起来 | 把总差分解到各通路 |
| 构造给定的事实 | 「**是什么**」，与测量无关 | 场景里放了哪几个目标 |
| 消融 / 干预 | 只能说「**改掉它会怎样**」，横着加不起来 | 换掉一个环节，指标动了多少 |

第三类最容易被误用——几个消融结果并排放，读起来像是把总量分解完了，其实它们的分母
根本不是同一个东西。如果一页里同时有这几类，**显式标出每个结论属于哪一类**，
并说明哪些能相加、哪些不能。

## 概念铺垫：用读者熟悉的领域类比

如果读者的背景不是这个领域，**先用他熟悉的东西搭桥，再上数据**。
好的类比不是修辞，是同构——比如向语音背景的读者解释射频的"干信比"和"时频重叠"，
可以指出语音分离和射频检测**用的是同一套方法**（都在时频图上找源），
"两个人同时说话且音高重合最难分"就是"两个发射机时频重合最难分"。
这种类比经得起追问；「就像鸡尾酒会一样嘈杂」这种经不起。

先确认读者背景再决定要不要这一节。背景相同的话，这节是累赘。

## 技术约束

**默认自包含。** 图片全部 base64 内嵌，不外链 CSS/JS/字体。这样一个文件就能发邮件、
拷 U 盘、离线打开。用 `assets/report_html.py` 的 `embed()`（PNG→WebP，约省 2.5 倍）。

**例外：证据本身需要被听/被播放时。** 音频、视频这类媒体内嵌会把页面撑到几百 MB，
这时改成「目录 + 相对路径」：`<audio controls preload="none" src="assets/xxx.wav">`。
`preload="none"` 很关键，否则一打开页面就并发拉取几十个文件。
**可听的证据往往比指标更有说服力**——语音增强报告里 PESQ 涨了多少是代理指标，
让人亲耳听一遍前后对比才是直接证据。这类报告整个目录一起交付，README 里写清体积。

**每个图表下面折一张数据表。** `<details><summary>数据表</summary>` 包住原始数字。
图是论点，表是证据：略读的人不受打扰，要核对的人不必来找你要数据。
这也是无障碍要求——颜色编码的图必须有等价的文本形式。

**给一个主题切换按钮。** 页面会跟随系统设置，但读者的机器和现场不是一回事：
亮色笔记本在暗会议室里，或者投影把暗色洗得看不清。
放一个 `<button class="theme-toggle" data-theme-toggle>☾ 深色</button>`，
`report_html.py` 的 `JS` 已经接好了切换逻辑。

**图表优先用内联 SVG，不用 PNG。** `assets/charts.py` 提供折线图（`panel`/`line_chart`）
和二维条件网格热图（`heatmap`/`heat_scale`）。SVG 体积小、缩放不糊、能跟随暗色模式、
能挂 hover 提示。只有谱图、照片这类位图才用 PNG。

**画任何图表前先读 dataviz skill**，尤其是配色。`charts.py` 里的色板和顺序色阶
已经按它验证过（14 组底色/文字对比度实测 ≥4.5:1），直接用即可；要自己调色就得重新验证。

**多个配置用 tab 对比，别并排堆。** 两套权重、两种数据源这类对比，用
`data-tabs` + `data-panel-<key>` 切换（`report_html.py` 的 `JS` 已实现）。
注意面板上**只写** `data-panel-<key>`，不要再加一个裸的 `data-panel`——
那会让切换逻辑永远判定为隐藏。给面板加 `class="tabpanel"`，打印时才不会丢内容。

**暗色模式要单独选色**，不是把亮色翻转。`report_html.py` 的 CSS 和 `charts.py`
的色阶都已经处理好；自己加的颜色记得在暗色下验对比度。

**大表格和长清单折进 `<details>`**，但默认展开主结果。

## 体检：渲染出来看

生成器跑通不等于页面是对的。**每次改完都跑一遍体检**：

```bash
node <skill>/scripts/check_page.cjs <报告目录>/index.html --shots /tmp/shots
```

需要 playwright（`npm i playwright && npx playwright install chromium`，
或把 `NODE_PATH` 指向已有的 node_modules）。

它检查的都是从生成器那一侧看不见、但用户一眼就会看到的东西：
重复 id、桌面与窄屏溢出（并指出是哪个元素撑宽的）、外链资源（破坏自包含）、
图片加载失败、sticky header 遮挡锚点、**tab 组是否真的能切出内容**、
暗色模式对比度不足、**亮色系统下能否强制切到暗色**、缺主题按钮、JS 报错。
有问题时退出码非零并列出来。

那条"强制暗色"看着琐碎，但它抓到过一个真实缺陷：暗色样式只写在
`@media (prefers-color-scheme: dark)` 里时，切换按钮只能强制亮、不能强制暗，
而后者恰好是亮色笔记本的读者会碰到的方向。暗色值要在**两个作用域**下各声明一次
（media query 管系统设置，`[data-theme=dark]` 管手动切换）——
`assets/charts.py` 的 `_dark_rules()` 就是这么做的。

然后**真的把截图看一眼**。体检查的是机械问题，看不出"这张图挤得没法读"——
上一轮就是靠看截图才发现单行 6 列的谱图被压扁，改成 2×3 折叠布局才可读。

## 交付的是一个目录，不只是一个页面

页面给领导，目录给同行和三个月后的自己。一个成形的报告目录长这样：

```
reports/<主题>/
  index.html        页面本身
  README.md         给开发者看的那一份
  data.json / *.csv 数据导出，页面不引用它，人才引用它
  assets/           音频、原图等页面引用的媒体（有才建）
```

**README.md 和 index.html 是写给两拨人的。** 页面回答"结论是什么"，
README 回答"这东西怎么来的、怎么重跑、和上一版差在哪"。有了它，
页面就不必为了自证而塞满方法学细节，可以专心把结论讲清楚。README 至少写：

- **起因**，以及指向上游报告的链接——报告之间有引用链才成体系，孤立的报告没人回头看
- **怎么重新生成**：完整命令序列，含每步大致耗时
- **体积及其构成**（例：`约 10.3 MiB，其中音频和频谱图占 9.1 MiB`）。
  这直接回答"能不能发邮件"，省掉一次往返
- **这一版和上一版差在哪**。如果是重做，说清上一版错在哪——
  否则读者会以为两版结论可以混着用

**导出一份数据。** `data.json` 或 `per_sample.csv` 放在页面旁边，不被页面引用。
CSV 尤其值钱：同事能直接拖进 Excel 自己切，而不必请你重跑一遍或者截图给他。

## 发布到端口

页面是自包含的，直接发文件也行。要给个链接就用：

```bash
<skill>/scripts/serve_report.sh start <报告目录> --port 8845
# 输出可直接发出去的 URL，例如 http://<本机在内网的地址>:8845/
<skill>/scripts/serve_report.sh status|stop|list
```

几个刻意的设计，如果你改写它请保留：

- **只绑一张网卡，不绑 `0.0.0.0`。** 实验机通常还挂着 IB 网和 docker 网桥，
  为了给一个同事看而全网发布，暴露面大得没必要。默认取出网路由的那个地址。
- **只发布报告目录，不发布仓库根。** 权重、原始数据、检查点因此不可达（已验证路径穿越返回 404）。
- **只读。** 不要为了"方便"换成带上传的服务。

多个报告可以各占一个端口（`--name` 区分），或者建一个索引目录放软链接统一发布。

## 资产

- `assets/report_template.py` — **生成器骨架，从这里起步**。拷走改名，把 `MARKER` 逐个换掉。
  开箱即跑（`--run` 指向任意含 `summary.json` 的目录），骨架、tab、热图、折线、
  缺失条件的画法都已接好。
- `assets/report_html.py` — 设计系统（`CSS`/`JS`）、`embed()`、`table_html()`、`escape()`、`signed()`
- `assets/charts.py` — 内联 SVG：`panel`/`line_chart`/`legend`、`heatmap`/`heat_scale`/`heat_step`，
  含亮暗两套色阶与 hover 层（`CHART_CSS`/`CHART_JS`）
- `scripts/check_page.cjs` — 渲染体检
- `scripts/serve_report.sh` — 端口发布

两个库 `.py` 拷到项目里 import 即可。**如果项目里已经有等价的模块就用项目的那份**，
不要拷贝出第二套——设计系统一分叉，两个页面看起来就不像一家的了。

## 交付前自查

- [ ] 页面里的数字都能在运行目录里找到出处，没有手敲的
- [ ] 标题是结论，不是主题
- [ ] 全条件证据齐全，失败和未跑成的都标了，且两者画法不同
- [ ] 写了"哪些失败是原理性的、哪些是能改的"；混用多类方法时标了证据强度
- [ ] 每个图表下面折着它的数据表
- [ ] 限制写在页内，和结论平级
- [ ] `check_page.cjs` 通过，且截图看过一遍
- [ ] 目录里有 README.md：起因与上游链接、重跑命令、体积、与上一版的差别
- [ ] 导出了一份 CSV/JSON 供别人自己分析
- [ ] 复现命令带哈希（配置/数据/权重）
- [ ] 同步更新项目的实验记录和首页（如果项目有这个约定）
